# 제안서 목차 샘플 분석과 활용 계획

작성: 2026-10-12 · 상태: **계획만 (구현 전)**

## 원칙: 원문은 저장소에 넣지 않습니다
- 분석 자료는 외부 판매 사이트의 제안서 샘플 목차 15종입니다. 원문 목차, 출처 URL, 상품 번호, 기관명, 금액은 저장소에 넣지 않습니다.
- 저장소에는 아래 **분포와 구조 규칙**만 남깁니다. 장 이름은 공공 제안서에서 흔히 쓰는 일반 용어만 씁니다. 세부 제목 문구는 직접 만듭니다.

## 1. 분석 결과 요약

| 지표 | 실제 샘플 | 현재 mock 시드 |
|---|---|---|
| 장 구성 | 5~7장. 일반현황 → 전략·방법론 → 기술·기능 → (성능·품질) → 사업관리 → 지원. 업체마다 장 이름·순서가 다르고, 장 구분이 없는 평면형도 있습니다 | 3업체 모두 같은 순서의 평면 8블록 |
| 목차 항목 수 | 문서당 24~290개 (중앙값 약 140) | 업체당 8개 |
| 깊이 | 장 아래 2~5단 (평균 약 3.5) | 1단 |
| 제목 길이 | 평균 11~20자, 최대 69자. 번호 체계가 섞여 있고(Ⅰ./1.1/가.) 중복 제목도 있습니다 | 2~6자 |
| 쪽수 | 제안서 110~140쪽 (제출 상한 200쪽) | 최대 약 54쪽 |
| 인쇄쪽 | 표지·목차·간지 때문에 구간마다 오프셋이 다르고, 간지·표 쪽은 쪽 번호가 없을 수 있습니다 | 상수 오프셋, 쪽 번호 없는 경우 1건 |
| 근거 위치 | 보안·품질은 한 업체 안에서도 2~3개 장에 흩어지고, 같은 기준이라도 업체마다 위치가 다릅니다 | 기준 1개 = 업체당 블록 1개 |

평가항목과 목차 장의 대응은 다음과 같습니다.
- 정렬이 쉬운 항목: 추진전략, 사업관리, 인력, 지원
- 중간 정도: 사업이해도, 기술, 기능
- 어려운 항목: 성능, 보안. 위치가 일정하지 않습니다.

→ **"기준 하나 = 쪽 범위 하나"로는 부족하고, "기준 하나 = 근거 여러 개"가 기본이어야 합니다.**

## 2. 활용 계획 (우선순위순)

| 순서 | 할 일 | 효과 | 비용 | 선행조건 |
|---|---|---|---|---|
| 1 | **mock 시드 생성기**: 업체 3곳에 서로 다른 장 골격을 줍니다(5장형, 품질특성형, 평면형). 블록은 업체당 120~200개, 문서는 80~140쪽, 인쇄쪽 오프셋은 구간별로 다르게 하고 간지 구간은 null로 둡니다. 기준은 7개에서 10~11개로 늘리고(기능·성능 추가) 일부 기준에 근거를 여러 개 연결합니다. 정적 데이터 대신 규칙과 고정 난수 시드로 생성합니다 | 원문 보기, 근거 서랍, 진행 격자를 실제 규모로 검증합니다. 발표 화면도 실제 문서처럼 보입니다 | 중 | 없음 (현재 계약 필드 안에서 가능). `SEED_VERSION`을 올립니다 |
| 2 | **스트레스 데이터**: 생성기 옵션으로 70자 제목, 5단 깊이, 250개 블록, 200쪽 문서, 쪽 번호 없는 연속 구간을 만듭니다 | 줄바꿈·스크롤·성능 문제를 미리 찾습니다 | 하 | 1 |
| 3 | **계약 확장 제안**: `Block`에 `level`, `section_path`, `order`, `page_end`를 추가하고, `Evidence`에 `page_end`(여러 쪽에 걸친 근거)를 추가합니다. `GET /documents/{id}/toc`를 신설합니다 | 원문 보기에 목차 탐색을 넣을 수 있고, 근거가 장 경로로 표시됩니다 | 하(문서) | 문서 분석 담당(DaeUng79)과 합의합니다. 실제로 hwpx에서 제목 계층을 뽑을 수 있는지가 관건입니다 |
| 4 | **공유 테스트 데이터**: 구조만 담은 JSON(장 골격, 깊이, 제목 길이 분포, 쪽 오프셋 규칙)에 기대 결과(계층, 쪽 범위, 기준 후보)를 붙여 AI·서버 담당과 함께 씁니다 | 파싱과 화면이 같은 가정을 공유합니다 | 중 | 3의 필드 이름 합의 |
| 5 | **목차 나란히 보기** (행=평가항목, 열=업체, 칸=근거 쪽 범위, 칸 클릭 → 원문) | 업체별로 다른 위치를 한 번에 비교합니다. 이 분석으로 필요성은 확인했습니다 | 중상 | **범위 재결정 필요.** 지난 시안 검토 때 범위 밖으로 미뤘던 항목이라 팀 합의가 필요하고, A/B 비교를 위해 두 트랙에 같은 범위로 넣어야 합니다 |

## 3. 하지 않을 것
- 원문 목차나 제목 문장을 그대로 시드에 복사하지 않습니다.
- 계약 확장 필드를 합의 전에 실제 모드 화면의 필수 전제로 쓰지 않습니다. mock 전용 선택 필드로만 씁니다.
- 생성 데이터로 확인한 결과를 인수 "통과"로 기록하지 않습니다.

## 4. 확인하지 못한 것
- 판매 사이트 이용 약관상 분석 목적 이용이 허용되는지 확인하지 못했습니다.
- 샘플 목차는 실제 낙찰 제안서의 분포와 다를 수 있습니다.
