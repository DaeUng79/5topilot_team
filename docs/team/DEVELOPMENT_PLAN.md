화면의 버튼별로 정상 동작뿐 아니라 새로고침, 권한 없음, 입력 누락, 중복 클릭, 서버 실패 시 동작을 이슈에 적습니다. 발표시간·질의응답시간은 문서 파싱이나 평가 점수와 별도 필드로 관리합니다. 각 단계의 완료 조건과 되돌리기 조건도 서버 상태로 합의합니다.

**사업의 평가 진행률과 개발 진척은 분리합니다.** 데모의 “평가 진행”은 위원 제출 등 사업 업무 상태입니다. 개발 진척은 GitHub Issues/Projects의 `Backlog → Ready → In progress → Review → Done`으로 관리합니다. `Blocked`는 사유·선행 이슈를 적고, 코드 병합과 공동 환경 검증·배포 상태를 별도 필드로 남깁니다.

## 4. 먼저 끝까지 연결할 최소 기능

첫 목표는 **가상 사업 1개 + 합성 HWPX 1개를 업로드해 평가기준 후보와 원문 쪽을 확인하고, 사람이 확정한 뒤 새로고침해 같은 결과를 조회하는 흐름**입니다. 이미 구현된 문서 처리에서 출발하면 화면·API·작업자·저장소의 연결 문제를 작게 확인할 수 있습니다.

1. Lex6won이 첫 흐름의 범위·인수조건을 조율하고 DaeUng79와 u-jing이 문서 등록·작업 상태·결과·확정 계약을 작은 PR로 합의합니다.
2. cookiesh1은 같은 계약의 mock으로 업로드·대기·실패·근거 확인 화면을 만듭니다.
3. DaeUng79는 기존 파서 호출을 어댑터로 감싸고 작업 요청·조회 API를 연결합니다. u-jing은 사업/기준·권한·확정 기록과 문서의 연결을 구현하고 상호 검토합니다.
4. 실제 테스트 파일로 mock을 서버 연결로 바꾸고 Lex6won이 인수 시나리오를 재현합니다. DaeUng79가 PR의 기술 통합을 조율합니다.
5. 동일 입력 재시도, 저장 실패, 근거 페이지 미확인, 원본 변경 후 재확정까지 검증한 후 다음 기능을 붙입니다.

데모에 PDF 파일명이 보인다는 사실은 현재 파서가 PDF를 지원한다는 뜻이 아닙니다. PDF/OCR은 지원 형식·추출 기준·검증 파일을 정한 별도 이슈로 둡니다. 스캔 문서에서 근거를 못 찾으면 검토 필요 상태를 표시하고 확정된 기준처럼 처리하지 않습니다.

## 5. 병렬 개발에 필요한 공통 계약

아래는 **설계 초안**입니다. 실제 필드명·경로·오류 코드는 기반 PR과 합의 후 `contracts/` 명세에 확정합니다.

| 계약 | 최소 합의 내용 |
| --- | --- |
| 식별·권한 | `project_id`, `document_id`, 업체·평가위원 식별자. 인증된 사용자에서 권한을 판정하며 요청 본문의 사용자 ID를 신뢰하지 않음 |
| 문서 출처 | `source_sha256`, `source_revision`, `block_id`/셀 참조, `physical_page_number`, `page_number`, 경고·검토 필요 여부. 물리 페이지와 인쇄 쪽번호를 구별 |
| 평가 지원 에이전트/챗봇 | 응답의 문서 근거마다 `document_id`, `source_revision`, 블록/셀, 물리 페이지·인쇄 쪽번호 연결. 해당 사업에서 접근 가능한 자료만 검색하며 근거 없음·상충·구버전은 표시. 답변은 평가 보조이며 점수 저장·자동 확정·제출 권한을 갖지 않음 |
| 작업 상태 | `job_id`, `queued/running/succeeded/failed`, 오류 코드, 재시도 가능 여부, 결과 revision. 오래 걸리는 파싱·OCR은 별도 worker 실행 |
| 기준 확인 | 기준 후보와 확정 기준 분리, 출처·배점·확정자·확정 시각·버전 기록. 원본 revision 변경 시 기존 확인의 유효성 재검토 |
| 평가 저장 | 평가표 ID, 항목 ID, 0점을 포함한 점수·의견, 서버 version. 오래된 version 저장과 제출 후 수정 거절 |
| 오류 | 사용자에게 표시할 메시지와 코드, 재시도 가능 여부. 권한·찾을 수 없음·입력 오류·버전 충돌·작업 실패를 구별 |
| 계산 | 배점, 누락 처리, 반올림, 동점, 최고·최저 제외, 가격평가 등 승인된 정책 버전. 미정 정책은 임의 기본값으로 운영하지 않음 |

각 계약에는 정상·빈 결과·권한 거절·검토 필요·충돌 예제를 함께 둡니다. mock 데이터와 서버 응답은 같은 스키마로 검증합니다. API 계약을 바꾸는 PR에는 소비자 화면과 회귀검증 영향을 적고, 깨지는 변경은 연결된 PR 순서를 정합니다.

PR #1의 명세 경로는 `contracts/openapi.json`, API 테스트는 `apps/api/tests/`, 전체 흐름 테스트는 `tests/e2e/`, CI는 `.github/workflows/ci.yml`입니다. 기반 PR을 채택할 경우 이 구조와 생성 도구를 이어 쓰고 같은 목적의 명세를 새 경로에 중복 생성하지 않습니다.

MongoDB/GridFS는 현재 문서 데이터 저장소이고 PostgreSQL은 기반 PR의 업무 데이터 저장소 제안입니다. 우선 API가 문서 ID·revision·파일 참조를 연결하도록 설계하고, 원문을 두 DB에 중복 저장하거나 기존 데이터를 즉시 옮기지 않습니다. 단일 저장소로 바꿀지는 복원·용량·운영 부담을 비교한 별도 결정으로 남깁니다.

문서·챗봇 계약은 DaeUng79가 작성하고 u-jing이 평가 기능에서 사용할 근거와 버전을 검토합니다. cookiesh1은 인용을 눌렀을 때 정확한 원문이 열리는지 확인합니다. Lex6won은 AI가 제공할 보조 범위와 인수조건을 기획에 반영합니다.

## 7. 이슈·PR·완료 운영

이슈에는 `목적 / 담당 / 검토자 / 변경 폴더 / 화면 / API·DB 영향 / 선행 이슈 / 인수조건 ID / 이번 범위 / 테스트 결과`를 기록합니다. 1~2일 안에 검토할 수 있는 크기로 나누고 기능 브랜치에서 Draft PR을 일찍 엽니다. 동일 파일·migration·공통 계약을 수정할 때는 이슈에서 선행 PR을 정합니다.

| 검토 단계 | 확인 내용 |
| --- | --- |
| 작성자 | 변경 범위, 정상·실패·권한 테스트, 계약·migration 동기화, 실행 커밋·명령·결과, 미실행 항목 |
| 동료 검토자 | 직접 재현, 다른 기능에 미치는 영향, 테스트 자료와 계산 근거, 실제 서버 연결 여부 |

공통 업무 DB migration은 u-jing과 DaeUng79가 검토된 파일로 관리하고 적용자를 정합니다. 위원 데이터에 영향이 있으면 Lex6won도 검토합니다. 개인 초기화·seed를 공동 DB에 실행하지 않습니다. 문서 변경만으로 GitHub 보호 규칙이나 CODEOWNERS 검토 의무가 활성화되는 것은 아니므로 적용 상태를 따로 확인합니다.

## 8. 온프레미스로 이어가는 구조

웹, 업무 API, 오래 걸리는 문서 worker, 업무 DB, 문서 저장소의 설정을 분리합니다. 파싱·OCR·페이지 렌더링은 긴 HTTP 요청에 붙이지 않고 작업 ID로 조회하며 재시도·타임아웃·실패 기록을 남깁니다. 클라우드와 온프레미스에서 같은 계약·fixture·검증표를 사용합니다.

최종 전환은 컨테이너 실행만으로 완료하지 않습니다. 계정·파일·데이터 이전, 저장소 어댑터, 작업자 복구, 백업 복원과 권한 검증까지 별도 마일스톤으로 확인합니다. 외부 AI 서비스 의존이 있으면 내부망 환경에서 대체 가능한지와 기능 제한을 기록합니다.
