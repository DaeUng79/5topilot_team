# 4인 공동 개발 방법

## 매일 반복할 흐름

1. 이슈에 기능·파일·담당·선행 작업·완료 기준을 적는다. 같은 파일이 겹치면 수정 순서를 합의한다.
2. 각자 독립 clone에서 최신 기준 브랜치로 작은 기능 브랜치를 만든다. 예: `feat/documents-upload`. 자동 작업 브랜치는 `codex/` 접두사를 쓴다.
3. 1~2일 안에 리뷰할 수 있는 PR로 나눈다. 화면→API→저장→검증을 한 번 연결하는 작은 기능을 우선한다.
4. API 응답·샘플을 먼저 합의하고 화면 담당은 mock으로 병렬 개발한다. 계약 변경은 제공자·소비자가 함께 리뷰한다.
5. 자신이 테스트한 뒤 동료가 인수 조건으로 교차 테스트한다. 본인 승인으로 리뷰를 대신하지 않는다.
6. CI·리뷰·선행 PR·DB 적용 순서를 확인해 DaeUng79가 통합을 조율한다. 공동 환경 재현 결과를 이슈에 남긴다.

GitHub Projects 제안 상태: `Backlog → Ready → In progress → Review → Integrated → Done`. 담당자·기능·우선순위·선행 이슈·목표 주차를 필드로 둔다. 이는 **개발 진행률**이며 데모의 **사업 평가 진행률**과 별개다. 이 문서는 보드·이슈를 실제 생성한 기록이 아니다.

## 공통 변경

- 계약, 인증, migration, CI, lockfile, 공통 UI는 관련 담당자에게 리뷰를 요청한다.
- DB 변경은 migration과 적용/복구 절차를 기록한다. 개인 DB, 통합 DB, 운영 DB를 구분한다.
- PR preview가 공동 DB 초기화·seed·migration을 자동 실행하지 않게 한다.
- 미실행 검증은 미실행으로 기록한다. 실패를 숨기려고 테스트를 제외하지 않는다.

## Lovable과 팀 저장소

**권장:** 데모를 화면 기준으로 삼고 필요한 원본 소스를 팀 저장소 `apps/web`로 가져오는 검토 PR을 만든 후 이 저장소에서 개발한다. 빌드된 JS/HTML을 원본 TSX로 간주하지 않는다. 원본 도입 시 dependencies·asset·route·API 연결도 함께 확인한다.

Lovable에서 직접 개발을 계속하려면 프로젝트 설정의 실제 연동 저장소·브랜치를 확인한다. 공식 문서상 연결 시 새 저장소를 만들며 기존 GitHub 저장소를 Lovable 프로젝트로 가져오는 기능은 지원하지 않는다. 따라서 `5topilot_team`과 이미 연결되었다고 가정하지 않는다. Lovable은 한 번에 한 브랜치를 편집·동기화하며 기본값은 기본 브랜치다. 기능 브랜치와 PR 검토 과정을 맞춰 사용한다.

원본 연동 저장소와 팀 저장소 양쪽에서 동일 파일을 동시에 편집하지 않는다. 원본을 한 번 가져와 팀 저장소를 기준으로 할지, Lovable 저장소를 프론트 전용으로 유지할지 정한다. 초기 4인 프로젝트에는 한 팀 저장소가 단순하다. 이번 작업에서는 연동 설정을 변경하지 않았다.

## 문서별 범위

- 루트 README: 제품 목적, 흐름, 구현 상태, 팀, 폴더, 실행 시작점.
- 개인 README: 확정 역할, 담당 코드, 실행법, 완료/진행/예정, 이슈·PR·테스트 증거, 의존 작업.
- `docs/modules/`: 입출력·DB·오류·제약 등 유지보수 설명.
- 이슈/PR: 변경 이유·완료 조건·실행 결과·리뷰. 일지에 전체 코드를 복사하지 않는다.

완료 처리는 계약 일치, 성공·실패 테스트, 동료 리뷰, 통합 환경 재현, 문서 갱신까지 확인한 뒤 한다.
