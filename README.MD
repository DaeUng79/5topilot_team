# 심사임당 — 협상에 의한 계약 자체평가 업무 지원 서비스

사업·제안요청서 준비, 평가위원 선정, 제안평가, 결과 취합과 보고를 하나의 흐름으로 연결하는 4인 팀 프로젝트입니다.

**팀원은 `apps/`의 담당 기능 폴더에서 개발하고, `docs/<GitHub 계정>/`에 설계·진행 상황·검증 결과를 기록합니다.** 

기획·발표 원본 자료는 `참고자료/`, 공동 인수 기준은 `docs/testing/`에서 관리합니다.

- [팀 저장소](https://github.com/DaeUng79/5topilot_team)
- [목표 화면 데모](https://simsa-ai.lovable.app/admin/projects/p1?tab=progress)
- [공동 인수검증표](docs/testing/ACCEPTANCE.md)

데모는 목표 화면을 참고하는 용도이며, 원격 PR·배포 상태는 이번 확인 범위에 포함하지 않았습니다.

## 팀 공동 목표

```text
제안요청서 등록·파싱 → 평가기준 검토·확정 → 제안서 등록 → 평가위원 선정·배정 → 개별 평가·제출 → 결과 취합·위원장 확정 → 보고·보관
```

각 기능을 연결해 위 흐름을 재현하는 것이 공동 목표입니다. 

현재 문서 처리 코드는 HWPX를 대상으로 하며, PDF·PPT 등 추가 형식 처리는 후속 개발 항목입니다. 

AI가 추출·생성한 요구사항과 평가기준은 사람이 검토·확정한 뒤 평가에 사용합니다.

## 무엇을 어디에 저장하나요?

| 저장할 내용                                                | 위치                              | 작성 원칙                                                  |
| ---------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------- |
| 구현 코드·의존성·기능 테스트                             | `apps/` 아래 담당 기능 폴더     | 기능별로 개발하고 다른 영역과 연결할 입력·출력을 명시     |
| 기능 실행·설정 방법                                       | 해당`apps/<기능_담당자>/README` | 실행 위치·명령·필요 설정·검증 결과를 코드와 함께 갱신   |
| 개인 목표·설계·진행 상황·회의 결정·Issue/PR·검증 기록 | `docs/<GitHub 계정>/`           | 개인 README를 목차로 사용하고 상세 문서는 같은 폴더에 추가 |
| 공동 인수 조건·전체 흐름 검증 계획                        | `docs/testing/`                 | 실제 실행 상태와 근거를 기록하고 미실행 항목을 구분        |
| 기존 팀 가이드·기획·설계·발표 원본                      | `참고자료/`                     | 원본 참고자료를 보관하고 최신 개발 결정은 담당 문서에 기록 |
| 이슈·PR 작성 양식과 리뷰 담당 설정                        | `.github/`                      | 팀 공통 협업 규칙 관리                                     |
| 프로그램이 입력으로 읽는 서식                              | `apps/documents_daeung/doc/`    | 코드와 함께 관리하고 변경 시 참조 경로 확인                |

`apps/`의 담당자 표기는 기능 책임을 나타냅니다. 전체 앱을 각자 복제하는 용도가 아닙니다. 

`docs/`는 설명과 기록, `참고자료/`는 원본 자료 보관에 사용합니다. 

API·데이터 구조 등 여러 기능에 영향을 주는 결정은 관련 담당자가 함께 검토하고 이슈·PR 및 담당 문서에 연결합니다.

## 공동 작업 순서

1. 이슈에 담당자, 목표, 변경 범위, 선행 작업, 완료 조건을 적습니다.
2. 담당 개발 폴더에서 작은 기능 단위로 작업하고, 여러 영역에 영향을 주는 API·DB 변경은 관련 담당자와 먼저 맞춥니다.
3. 기능 테스트와 연결 시나리오를 검증한 뒤 개인 문서에 실제 결과를 남깁니다.
4. 기능 README·개인 문서를 함께 갱신해 PR을 만들고 동료 리뷰를 받습니다.
5. Lex6won은 기획·인수 조건을, DaeUng79는 병합 순서·통합 검증을 조율합니다.

로컬 완료, PR 작성, 병합, 배포, 인수 통과는 구분해서 기록합니다.`.env`·API 키·DB 접속정보·실제 제안서·개인정보·생성 산출물은 Git에 올리지 않고, 공유 테스트에는 합성 데이터를 사용합니다.
