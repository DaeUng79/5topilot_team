01 / TEAM AGREEMENT

팀원 모두가 기억할 다섯 가지

  1. 시작 전에 알립니다. 열린 이슈·PR을 확인하고 작업 내용, 파일, 브랜치, 완료 기준을 이슈에 남깁니다.
  2. 필요하면 다른 영역도 수정합니다. 관련 담당자에게 알리고 리뷰를 받습니다. 공통 파일이나 같은 파일을 동시에 바꿀 때는 먼저 순서를 합의합니다.
  3. 기능별로 짧게 작업합니다. 사람별 영구 브랜치 대신 작은 기능 브랜치와 1~2일 규모 PR을 권장합니다.
  4. main은 DaeUng79가 통합합니다. 다른 팀원의 리뷰와 자동 검증을 거쳐 Squash merge합니다. 본인 PR도 동료 리뷰를 받습니다.
  5. 공동 DB는 임의로 바꾸지 않습니다. DB 변경 파일을 PR에 포함하고 검토·적용 순서를 정합니다. 개발에는 가짜 데이터만 씁니다.

역할 = 품질과 리뷰의 책임. 다른 사람이 해당 폴더를 수정할 수 없다는 뜻이 아닙니다. 다만 알림 없이 범위를 넓히거나 남의 변경을 덮어쓰지는 않습니다.

02 / PRODUCT & EVIDENCE

무엇을 만드는 프로젝트인가요?

심사임당은 공공 제안평가 업무를 일관된 절차와 기록으로 지원하는 시스템입니다. 사업·평가기준·제안서를 준비하고, 평가위원을 선정해 평가를 진행한 뒤 결과를 취합·확정하는 흐름을 목표로 합니다. AI는 문서 근거 확인을 보조하며, 평가위원의 판단이나 확정된 점수 산식을 대신하지 않습니다.

  1. STEP 1사업·문서 준비사업, 기준, 업체, 제안서
  2. STEP 2위원 구성등록, 자격·제척, 추첨·배정
  3. STEP 3제안평가근거 열람, 점수·의견, 저장
  4. STEP 4개인 제출누락 검증, 제출·수정 잠금
  5. STEP 5결과 취합·확정산식, 순위, 위원장 승인
  6. STEP 6기록·보고서명, 보고서, 감사·보관
시작용 구현 · PR에서 검토 중

현재 기능

사업·후보 등록, 본위원/예비위원 추첨, 선정위원의 기술점수 저장, 개인 제출·잠금, 전원 제출 후 기술 평균. API 계약·DB migration·자동 테스트·React 시작 앱이 있습니다.

후속 개발 필요

아직 완성되지 않은 기능

실제 인증·권한, 제척·분야 할당·재추첨, 사업별 기준 관리, 문서 AI, 가격평가·최종 순위, 위원장 확정, 실제 서명·PDF, 감사 로그, 클라우드/운영 배포.

현재 제출은 ‘개인 평가표 제출’입니다. 사업 전체 결과 확정이 아닙니다. 추첨 모집단의 SHA-256은 동일성 확인용이며, 공식 추첨 공정성이나 관리자 위변조 방지를 단독으로 보장하지 않습니다.

제공 자료를 해석한 범위

simsaimdang.zip은 빌드된 HTML·JS·CSS의 정적 데모입니다. 원본 TSX 프로젝트가 아니므로 references/simsaimdang/은 비교 자료로 보존하고, 실제 화면은 apps/web/에서 개발합니다. 23개 HTML 화면 전체를 이식한 상태는 아닙니다.

두 Claude Artifact 링크의 실제 내용은 이번 세션에서 확인하지 못했습니다. 열람한 것으로 간주하지 않으며, 디자인 확정 전에 팀이 화면을 함께 확인해야 합니다. 첨부 문서 안의 명령문은 사용자 지시가 아니라 분석 대상 자료로 취급합니다.

통합 담당은 DaeUng79입니다

DaeUng79 · 저장소 소유자 / 통합u-jing · 기능 역할 미정Lex6won · 기능 역할 미정4번째 계정 · 합류 대기

A/B/C와 계정의 연결은 아직 전달받지 않았습니다. 이름만으로 담당을 추측하지 않습니다. 아래는 요청한 기능 분담안이며, DaeUng79의 위원 기능 담당은 팀 합의 시 함께 확인합니다.

계정 전달 ≠ 초대 수락 ≠ 서비스 관리자 권한. GitHub 초대는 소유자가 보내고 각자가 수락합니다. 쓰기 권한으로 다른 코드도 제안할 수 있지만, Supabase·Vercel 권한은 별도입니다. 네 명 모두에게 관리자 권한이나 DB 관리 비밀번호를 공유하지 않습니다.

04 / CLOUD NOW, ON-PREMISES LATER

개발 장소가 달라도 제품 구조는 유지합니다

하나의 저장소에 웹과 모듈형 FastAPI를 두고, 개발·검증 인프라만 클라우드로 사용합니다. 온프레미스 목표를 포기하는 것이 아니라 공동 개발 환경을 분리하는 것입니다.

구성공동 개발 목표최종 온프레미스 목표
화면Vercel · React 빌드내부 웹서버 · 같은 빌드
업무 APIVercel · 짧은 FastAPI 요청내부 FastAPI 컨테이너
DBSupabase PostgreSQL내부 PostgreSQL · 같은 migration
AI·PC 제어별도 개발 PC/실행 서버내부 AI 서버·업무 PC
파일·인증비공개 저장소·실제 인증을 선정 후 연결내부 저장소·인증으로 교체/이전
  • 브라우저 → 업무 API → DB를 기본 경로로 합니다. 추첨·제출·점수 계산 규칙을 화면이나 Supabase 전용 함수에 흩어 놓지 않습니다.
  • 기존 computer_agent.py를 웹 API에서 바로 import하거나 사용자의 명령을 그대로 PC 제어 API에 전달하지 않습니다. A가 제한된 문서 기능을 어댑터로 분리합니다.
  • Supabase를 DB로만 쓰면 표준 PostgreSQL로 이전하기 쉽습니다. Auth·Storage를 추가하면 사용자·파일 이전도 별도 계획에 넣습니다. 전체 Supabase 자체 호스팅도 가능하지만 운영 부담은 커집니다.
  • 개인 개발 DB, 공동 통합 DB, 실제 운영 DB를 구분합니다. 미리보기 배포가 공동 DB migration/seed를 자동 실행하면 안 됩니다.
  • 실제 개인정보·제안서 대신 가짜 데이터로 개발합니다. DB 비밀번호와 서버용 키는 서버 환경변수에만 저장합니다.

위 표는 목표 구조입니다. Vercel·Supabase 실제 배포는 아직 하지 않았고 임시 인증은 공개 배포에 사용할 수 없습니다. Vercel 플랜별 협업·상업 이용 제한과 비용은 연결 전에 확인합니다.

06 / COLLISION PLAYBOOK

겹치면 더 빨리 덮어쓰지 말고, 순서를 정합니다

① 다른 담당 영역을 수정해야 할 때

이슈에 이유·파일을 추가하고 담당자를 태그합니다. 예: D가 위원 화면을 고치면 B에게 알리고 UI 리뷰를 받습니다. 담당 미정이면 DaeUng79가 조율합니다. 작은 독립 수정은 알림 후 진행할 수 있지만 공통 계약은 먼저 합의합니다.

② 같은 파일을 두 사람이 수정할 때

선행 PR과 후행 PR을 정합니다. 선행 변경을 먼저 합치고 후행 작업자가 최신 main을 반영합니다. 가능하면 공통 계약을 먼저 작은 PR로 합치거나 파일을 분리합니다. 파일 전체 포맷 변경과 기능 변경을 한 PR에 섞지 않습니다.

③ Git 충돌이 났을 때

두 작성자가 의도를 비교합니다. “내 것/상대 것 전부 선택”으로 해결하지 않습니다. 합친 뒤 양쪽 기능 테스트와 전체 흐름을 재실행합니다. 텍스트 충돌이 없어도 API 의미나 DB 가정이 달라질 수 있습니다.

④ API·DB·공통 설정을 바꿀 때

main.py, 인증, DB 연결, 공통 CSS, 의존성 lockfile, API 계약, migration, CI는 먼저 알립니다. 담당자와 소비자가 변경·병합·배포 순서를 합의합니다. 잠금 파일과 생성 타입은 도구로 다시 생성합니다.

⑤ 급한 수정 또는 AI 도구를 사용할 때

작은 fix/… 브랜치도 알림·PR·검증을 유지합니다. AI에는 이슈와 변경 범위를 전달하고 AGENTS.md를 읽게 합니다. 다른 사람의 미커밋 변경, 공유 브랜치, 공동 DB를 덮어쓰지 않습니다. 작성자가 생성 결과와 테스트를 책임집니다.

하지 않는 것: 다른 사람 브랜치에 무단 push, 공유 브랜치 force push, 오래된 전체 폴더 복사, main 직접 수정, 공용 로그인 사용, 공동 DB 초기화, 비밀키·실데이터 업로드.

07 / BRANCHES & MERGE AUTHORITY

누구나 제안하고, 통합 담당자가 합칩니다

저장소 소유자가 팀원을 초대하고 수락이 완료되면 각자 브랜치에 코드를 올립니다. CODEOWNERS는 검토 책임을 표시할 뿐 파일 수정 권한을 제한하지 않습니다. 계정별 A/B/C 역할이 확정될 때까지 기본 검토자는 DaeUng79로 유지합니다.

일반 팀원: 초대 수락 후 원본을 clone한 경우

git status
# 미커밋 작업이 있으면 먼저 해당 작업 브랜치에 안전하게 저장
git switch main
git pull --ff-only origin main
git switch -c feat/이슈번호-기능명
# 개발 → 테스트 → 변경 확인
git diff
git add 변경한파일1 변경한파일2
git commit -m "feat(영역): 변경 요약"
git push -u origin feat/이슈번호-기능명
gh pr create --base main --draft
# GitHub에서 준비 완료로 바꾸고 리뷰 요청

위 ‘이슈번호·기능명·변경한파일’은 실제 값으로 바꿉니다. gh가 없으면 GitHub 웹에서 PR을 만듭니다. 이미 만든 작업 브랜치에서는 다시 새 브랜치를 만들지 않습니다.

개발 중 main 변경 반영

# 현재 작업을 커밋한 기능 브랜치에서 실행
git fetch origin
git merge origin/main
# 충돌이 있다면 공동 확인 → 해결 → 테스트 → commit → push

기존 fork clone은 remote 이름이 다를 수 있습니다. 먼저 git remote -v로 원본/개인 fork를 확인하세요. 이번 작업 환경은 origin=원본, fork=Lex6won fork입니다. 쓰기 권한 수락 전에는 fork 브랜치에서 원본으로 PR을 보냅니다.

개인 저장소에 맞춘 두 겹의 main 보호

01

main-quality

PR, 작성자 외 승인 1개, 최신 변경 재승인, 대화 해결, verify 통과, 최신 main 반영. 강제 푸시·삭제 금지. 품질 규칙에는 우회자를 두지 않습니다.

02

main-integrator

main 업데이트를 제한하고 관리자 역할에 PR을 통한 예외만 부여합니다. 현재 개인 저장소 소유자 DaeUng79가 통합합니다. 01의 리뷰·검증 요건은 그대로 적용됩니다.

설정 파일은 docs/github-rulesets/에 Disabled 초안으로 준비했습니다. 저장소에 파일이 들어갔다고 보호가 켜지는 것은 아닙니다. 소유자가 설정 화면에서 가져오고 확인한 뒤 두 규칙을 Active로 바꿔야 합니다.

본인 PR도 남이 검토합니다. 현재 유일한 CODEOWNER는 DaeUng79이므로 code owner 승인을 필수로 켜면 본인 PR이 막힐 수 있습니다. 초기에는 이 옵션을 끄고 다른 쓰기 권한 팀원의 승인을 받습니다. 조직 저장소로 옮기면 통합 담당 팀 기준으로 권한을 재설계합니다. 관리자는 규칙 자체를 수정할 수 있습니다.

08 / CONTRACTS BEFORE IMPLEMENTATION

화면·API·DB가 같은 약속을 보게 합니다

API 변경의 기준

  1. 작업 이슈에 요청·응답 예시, 필수 값, 권한, 오류 조건을 먼저 씁니다.
  2. 백엔드 Pydantic 모델/라우터를 수정합니다. 프론트 담당은 같은 계약으로 개발합니다.
  3. apps/api에서 python ../../scripts/export_openapi.py, 루트에서 npm run contracts:types를 실행합니다.
  4. 생성 명세와 타입을 함께 커밋합니다. 생성 파일을 손으로 고치지 않습니다.
  5. 필드 삭제/이름 변경은 소비자와 함께 처리합니다. 먼저 추가 → 소비자 이전 → 제거하는 호환 변경을 우선합니다.

예: 이미 추첨 / 오래된 평가 버전은 409, 잘못된 입력은 422. 실제 세부 응답은 contracts/openapi.json이 기준입니다. 타입 일치만으로 업무 규칙이 맞는 것은 아니므로 테스트도 필요합니다.

DB 변경의 기준

  • 각자 모델/migration 초안을 작성할 수 있고 C가 관계·인덱스·변경 순서를 검토합니다. 공동 DB 적용은 D와 조율한 지정자만 실행합니다.
  • 병합·배포된 migration은 고치지 않고 새 revision을 추가합니다. 병합 전 Alembic head가 하나인지 확인합니다.
  • Supabase 대시보드에서 수동 테이블 변경을 하지 않습니다. 불가피한 복구는 사전 승인하고 즉시 변경 이력을 코드와 맞춥니다.
  • 공동 환경 적용 기록: 실행자, 시간, 이전/새 revision, 백업 필요 여부, 적용 결과, 후속 점검. PR별 자동 reset/seed는 금지합니다.
  • Vercel 런타임 연결은 transaction pooler와 제한된 풀을 사용하고 prepared statement·TLS를 설정합니다. migration은 별도 관리 연결을 사용합니다. 현재 클라우드 연결 설정은 구현 전입니다.
  • FastAPI만 DB에 접근한다면 불필요한 Supabase Data API 노출을 끕니다. 직접 Data API를 사용하는 설계를 채택할 경우 RLS·권한 정책을 별도로 검증합니다.
  • 코드 revert는 DB 복구가 아닙니다. 데이터 삭제가 포함되면 백업·복원 계획과 호환 배포 순서를 먼저 검토합니다.
09 / DEFINITION OF DONE

“내 화면에서 됨”을 넘어 함께 검증합니다

PR 작성자

  • 이슈와 변경 범위·사전 알림 연결
  • 정상·실패·권한 조건 테스트
  • API 명세·타입·migration 동기화
  • 실행한 명령과 결과 기재
  • 미실행 테스트와 미완성 범위 명시

검토자 / 통합 담당자

  • 담당 영역·소비자 영향 확인
  • CI 통과, 미해결 대화 확인
  • 최신 main과 함께 동작 확인
  • DB·API·화면 배포 순서 확인
  • Squash merge 후 전체 흐름 점검

통합 체크리스트

  • 후보 등록 → 적격 후보 → 본위원/예비위원 선정이 연결된다.
  • 중복·동시 추첨은 하나만 확정된다. 선정 결과가 새로고침 후 유지된다.
  • 선정위원만 본인 평가표를 작성한다. 예비위원·다른 사업 위원은 거절된다.
  • 0점은 유효하고, 누락·배점 초과·중복 항목은 거절된다.
  • 저장 후 재조회가 일치하며, 오래된 version 저장은 충돌로 처리된다.
  • 제출 후 수정·중복 제출·동시 저장으로 잠금을 우회하지 못한다.
  • 전원 제출 전 결과 노출을 막고, 제출 후 기술 평균이 정확하다.
  • 후속 구현된 제척·가격 산식·서명·위원장 확정·보고서를 같은 흐름에 붙여 검증한다.

현재 CI는 Python 검사, SQLite·PostgreSQL 테스트, migration/모델 차이, API 계약 차이, 프론트 빌드와 E2E를 검사합니다. 기존 PC 제어는 CI에서 실행하지 않습니다. 현재 테스트가 통과해도 실제 인증·서명·운영 보안이 완성됐다는 의미는 아닙니다.

문서 작성 시 연결 계정 Lex6won에는 원본 저장소의 push/admin 권한이 없습니다. 이 변경은 개인 fork의 기능 브랜치를 통해 원본 PR #1에서 검토하도록 준비합니다. main 반영, 계정 초대, 규칙 활성화, 외부 배포가 완료됐다고 간주하지 마세요. 최신 상태는 PR과 저장소 설정이 기준입니다.

A. DaeUng79가 할 일 — 팀원 초대

  1. 브라우저의 GitHub 프로필을 눌러 DaeUng79 계정으로 로그인했는지 확인합니다. 다른 팀원 계정으로는 원본 저장소 권한을 부여할 수 없습니다.
  2. 저장소에 들어가 상단 Settings를 클릭합니다. 화면이 좁으면 메뉴 더보기에서 찾습니다.
  3. 왼쪽 Access 영역의 Collaborators를 엽니다. 요청되면 본인 인증/2단계 인증을 완료합니다. 비밀번호나 인증 코드를 팀원에게 보내지 않습니다.
  4. Add people을 눌러 u-jing을 검색합니다. 표시되는 정확한 계정을 선택하고 초대를 전송합니다.
  5. 같은 방법으로 Lex6won을 초대합니다. 네 번째는 정확한 아이디를 받은 뒤 초대합니다. 소유자 자신은 추가할 필요가 없습니다.
  6. 각자에게 “GitHub 초대를 보냈으니 본인 계정에서 수락해주세요”라고 알립니다. Pending invitation은 아직 수락 전입니다. Collaborators 목록에서 수락 완료를 확인합니다.

개인 저장소에서는: 공동 작업자로 초대하면 읽기·쓰기 권한이 생깁니다. Organization에서 사용하는 Write/Maintain/Admin 역할 선택 화면과 다를 수 있습니다. 팀원에게 관리자 권한을 줄 필요는 없습니다. 공개 저장소를 볼 수 있거나 clone할 수 있다는 사실만으로 쓰기 권한이 확인되지는 않습니다.

B. u-jing / Lex6won / 새 팀원이 할 일 — 수락과 확인

  1. 초대받은 본인 GitHub 계정으로 로그인합니다. 다른 계정으로 열었다면 로그아웃/계정 전환부터 합니다.
  2. GitHub 알림 또는 초대 이메일의 저장소 초대를 열고 Accept invitation을 선택합니다. 초대가 안 보이면 소유자에게 Pending 여부와 계정 철자를 확인해 달라고 요청합니다.
  3. 원본 저장소의 Code → HTTPS 주소로 각자 PC에 clone합니다. 이미 clone했다면 git remote -v로 원본과 fork를 구분합니다.
  4. Git을 사용할 때 인증한 계정도 본인 계정이어야 합니다. git config user.name과 user.email은 커밋 표기일 뿐 접속 권한이 아닙니다.
  5. 작은 작업 이슈를 만들고 chore/이슈번호-onboarding 브랜치에서 문서 한 줄 같은 실제 변경을 커밋·push한 뒤 Draft PR을 만듭니다. 이것으로 쓰기와 PR 흐름을 확인합니다. main에 직접 push해 시험하지 않습니다.
  6. 소유자에게 PR 링크를 보내고 리뷰를 요청합니다. 초대 수락만으로 main 보호가 생기지 않으므로 규칙 설정 전에도 직접 main을 수정하지 않습니다.

GitHub CLI를 쓴다면 gh auth status로 로그인 계정을 확인하고 필요 시 gh auth login으로 본인이 로그인합니다. 토큰을 카톡·이슈·HTML에 붙여 넣지 않습니다. Git의 자격 증명이 다른 계정이면 자격 증명 관리자/본인 인증 흐름을 확인합니다.

C. DaeUng79가 할 일 — main 보호를 실제로 켜기

아래 버튼으로 설정 JSON 2개를 저장할 수 있습니다. HTML 첨부 하나만 있어도 다운로드됩니다. 실행 명령이나 비밀키는 들어 있지 않으며, 가져온 뒤에도 초기 상태는 Disabled입니다.

  1. 먼저 적어도 한 명의 동료가 쓰기 권한 초대를 수락했는지 확인합니다. A/B/C 역할도 합의해 기록합니다. 단독 개발 상태에서 필수 동료 리뷰를 켜면 병합할 수 없습니다.
  2. PR #1의 Checks를 확인합니다. 외부 기여 워크플로 승인 요청이 있으면 코드 내용을 확인한 뒤 Approve and run workflows를 선택합니다. 검사 결과에 verify가 실제로 나타나는지 확인합니다.
  3. Settings → Rules → Rulesets로 이동합니다. New ruleset 메뉴의 Import a ruleset에서 JSON을 하나씩 가져옵니다. UI 표기는 버전에 따라 조금 다를 수 있습니다.
  4. main-quality: 대상이 main, bypass list가 비어 있는지 확인합니다. PR 필수, 승인 1개, 마지막 push 작성자 외 승인, 새 변경 시 기존 승인 무효, 대화 해결, 최신 main 반영, 상태 체크 verify, 삭제·force push 금지를 확인합니다. 체크 출처 선택이 가능하면 GitHub Actions로 제한합니다.
  5. main-integrator: 대상이 main, Restrict updates가 선택됐는지 확인합니다. bypass 대상은 Repository admin 역할, 모드는 For pull requests only여야 합니다. Write 역할 전체를 예외에 넣지 않습니다.
  6. 두 규칙을 각각 Active로 바꾸고 저장합니다. main-integrator에서의 예외가 별도 main-quality까지 면제하지 않도록 품질 규칙의 bypass list는 비워 둡니다.
  7. Settings → General → Pull Requests에서 Allow squash merging을 켭니다. 팀은 Squash merge를 사용하며, Automatically delete head branches를 켜면 병합 후 작업 브랜치 정리가 편합니다.
  8. 시험 PR에서 팀원은 리뷰할 수 있지만 병합 권한은 제한되는지, DaeUng79도 승인·CI 충족 전에는 병합할 수 없는지 확인합니다. 강제 푸시나 main 직접 변경으로 검증하지 않습니다.

처음 도입할 때 검사 자체가 안 뜬다면: 원본 저장소의 Actions 허용 설정과 외부 PR 실행 승인부터 확인합니다. 초기 PR에서 원본 검사를 실행할 수 없다면, 소유자가 fork의 해당 커밋 CI 결과와 동료 리뷰를 확인한 후 기반 PR만 먼저 병합하고 원본 main의 첫 verify 실행을 확인합니다. 그 다음 두 Ruleset을 활성화합니다. 아직 실행되지 않는 체크를 먼저 필수로 걸어 초기 병합을 막지 않습니다. 보호 활성화 전에는 팀에 main 변경 중지를 알립니다.

JSON 가져오기가 안 보이면 — 수동 설정

New branch ruleset으로 이름과 main 대상을 지정해 위 ④의 품질 규칙을 만들고, 별도 규칙으로 ⑤의 업데이트 제한을 만듭니다. 처음엔 Disabled로 저장하고 표시값을 검토한 후 Active로 변경합니다. 체크 이름을 임의로 새로 쓰지 말고 실제 실행된 verify를 확인하세요. ‘Waiting for status to be reported’가 계속되면 체크 이름·실행 승인·워크플로 실행 여부부터 확인합니다.

D. 첫 PR을 검토하고 합치는 순서

  1. 작성자는 변경 요약·실행한 테스트·DB/API 영향과 미완성 부분을 적고 Draft를 Ready for review로 전환합니다. Reviews에 관련 담당자를 요청합니다.
  2. 검토자는 Files changed에서 코드를 보고, Review changes → Approve 또는 Request changes를 남깁니다. 작성자 본인의 승인으로 대체할 수 없습니다.
  3. 수정이 필요하면 같은 기능 브랜치에 커밋·push합니다. PR은 자동 갱신됩니다. 새 변경 후 리뷰와 검증을 다시 확인합니다.
  4. DaeUng79가 Checks·리뷰·미해결 대화·선행 PR을 확인한 뒤 Squash and merge → Confirm squash and merge합니다. 본인이 작성한 PR은 다른 팀원이 검토합니다.
  5. 병합 링크와 변경 영향을 이슈/카톡에 공유합니다. 팀원은 작업을 저장한 뒤 최신 main을 반영합니다. DB migration 적용이나 배포는 별도 단계이므로 완료 여부를 따로 알립니다.

Supabase/Vercel 초대는 GitHub 초대와 별개입니다. 각 서비스의 소유자가 필요한 사람만 프로젝트/팀에 초대하고, 개발자·조회자·관리자 권한을 구분합니다. 서비스 계정 주인이 GitHub 소유자와 같다고 가정하지 않습니다. 프로젝트 설정·권한·인증·비용 확인 전에는 계정을 공동 사용하거나 비밀키를 배포하지 않습니다.
