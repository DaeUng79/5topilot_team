# 팀 웹 화면

담당: **현수환 · cookiesh1**

메인·사업·문서·위원·평가·결과 6단계 화면, 공통 UI, mock→API 연결, 로딩·빈·오류·권한 상태를 다룹니다. 화면 방향과 결정 근거는 [UI_DIRECTION](../../docs/cookiesh1/UI_DIRECTION.md)에 있습니다.

## 스택

- React 19 + Vite + TypeScript + React Router 7, 순수 CSS(KRDS 색·글꼴 토큰)
- 글꼴: Pretendard GOV 동적 서브셋(`public/fonts/pretendard-gov`, OFL)
- API: `openapi-fetch`(생성 타입 `src/api/schema.d.ts`)와 제안 계약(`src/api/contract.ts`, 담당자 미합의 초안)
- `/api` 요청은 `127.0.0.1:8000`(apps/api)으로 프록시됩니다.

## 실행

Node 22.12 이상, 이 폴더에서 실행합니다.

```bash
npm install
npm run dev                  # 실제 API(127.0.0.1:8000) 연결
VITE_USE_MOCK=1 npm run dev  # API 없이 mock 데이터로 실행 (PowerShell: $env:VITE_USE_MOCK='1'; npm run dev)
npm run typecheck
npm test                     # Vitest: mock 응답 규칙·임시보관·CSV 파서
npm run build
```

화면 주소: http://127.0.0.1:5173

### 제안요청서 실제 파일 연계

`제안요청서 등록` 화면에서 HWPX 원본을 파싱하고 SQLite에 저장하려면 저장소 루트와 이 앱 폴더에서 각각 서버를 실행합니다.

```bash
# 저장소 루트: 문서 API (127.0.0.1:8001)
.venv/bin/python apps/documents_daeung/step0_documents_api.py

# apps/web_cookiesh1: 기존 사업·로그인은 mock 데이터, 제안요청서는 실제 파일 사용
VITE_USE_MOCK=1 VITE_RFP_API=1 npm run dev
```

사업 상세의 **제안요청서 등록**에서 HWPX 파일을 선택하면 파일 본문을 `/document-api/projects/:id/rfp`에 전송합니다. 문서 API가 `step1_hwpx_parse_to_JSON.py`로 파싱하고 `step2_hwpx_save_to_SQLite.py`로 원본·파싱 결과·이미지를 `apps/documents_daeung/documents_parse.sqlite3`에 저장합니다. 사업 ID와 사업명도 함께 저장하며, 같은 사업에서 새 파일을 올리면 화면의 버전 번호가 올라갑니다. 완료 후 화면에 쪽·블록·파싱 경고 수를 표시합니다. 파일 제한은 HWPX, 50MB입니다.

파일 저장이 끝나면 `step3_ai_requirements_extract_to_SQLite.py`가 자동으로 제안 요구사항을 추출해 같은 SQLite 파일에 저장합니다. 화면 아래 **제안 요구사항**에서 진행 상태와 사업현황·요구사항 총괄표·세부 내역을 확인할 수 있습니다. 추출에는 저장소 루트 또는 `apps/documents_daeung`의 `.env`에 `OPENAI_API_KEY`가 필요하며, 문서 내용이 OpenAI API로 전송됩니다. 추출에 실패하면 원본 파일은 보존되고 화면에서 재시도할 수 있습니다.

이 기능을 연결하기 전에 등록된 문서는 **제안 요구사항 → 요구사항 추출** 버튼으로 처리할 수 있습니다. AI 호출 없이 문서 업로드·조회만 사용하려면 문서 API를 `--no-ai` 옵션으로 실행합니다.

**평가기준 확정** 메뉴에서 `step4_ai_criteria.py`가 `documents_parse.sqlite3`에 저장한 정성적 평가기준 초안을 조회할 수 있습니다. 요구사항 추출이 끝난 문서는 **평가기준 초안 생성** 버튼으로 생성하며, 평가부문·항목·기준·요소·배점, 설정 이유, 보완 제안 항목을 표시합니다. 생성 과정은 저장된 요구사항을 OpenAI API로 전송합니다. 이 연동 화면의 최종 사람 확정 기록은 아직 SQLite에 저장되지 않습니다.

시연 데이터로 확인할 때는 업로드가 잠기지 않은 준비 단계 사업(`p2`)이나 새 사업을 선택합니다. SQLite 파일은 서버 시작 시 만들어지고, 첫 업로드 전에는 등록 문서가 없습니다.

`VITE_RFP_API=1`을 사용하면 이 화면의 제안요청서 상태와 단계 완료 여부가 SQLite의 최신 등록 파일을 기준으로 표시됩니다. 평가기준 AI 생성, 제안서 업로드 등 다른 메뉴는 기존 연결 상태를 따릅니다. 문서 API는 로컬 개발용이며 127.0.0.1에서만 열립니다.

## 화면 구조

앱은 로그인 전 공통 화면과 역할별 작업 공간으로 나뉩니다. 로그인한 사용자는 권한에 맞는 홈으로 이동하고, 다른 역할의 주소에 접근하면 권한 안내 화면이 표시됩니다.

```text
앱 공통
├─ 첫 화면 / 로그인
├─ 관리자 작업 공간
│  ├─ 왼쪽 고정 메뉴: 대시보드, 사업 관리, 평가위원 후보
│  ├─ 대시보드: 오늘 처리할 일, 진행 중 사업
│  ├─ 사업 관리: 사업 목록·검색·등록
│  └─ 사업 상세
│     ├─ 사업 요약
│     ├─ 1. 제안요청서 등록
│     ├─ 2. 평가기준 확정
│     ├─ 3. 제안서 등록
│     ├─ 4. 평가위원 선정
│     ├─ 5. 평가 진행
│     ├─ 6. 결과·위원장 확인
│     └─ 7. 보고·완료
└─ 평가위원 작업 공간
   ├─ 상단 헤더: 서비스 이름, 현재 사업명, 사용자, 로그아웃
   ├─ 배정된 평가 목록
   └─ 사업별 평가
      ├─ 평가 안내·서약
      ├─ 평가 홈: 사업 정보와 제안사별 진행 현황
      ├─ 문서 보기·질의응답
      ├─ 평가표 작성·저장
      ├─ 제출 전 점검·제출
      └─ 위원장 결과 확인
```

관리자 사업 상세에서는 사이드바의 단계 메뉴와 본문 상단 단계 이동을 함께 제공하며, 현재 단계와 완료된 단계를 표시합니다. 평가위원 사업 화면에서는 접을 수 있는 왼쪽 레일로 평가 홈, 문서, 평가표, 제출 화면을 오가고, 문서 목록과 입력 진행 상태를 확인합니다. 평가표 화면의 근거 원문은 별도 드로어로 열립니다.

### 주요 경로 및 화면

| 단계                | 경로                                             | 화면이 대응하는 인수 ID (화면 표시만 / 서버 검증 필요)                                                                         |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 첫 화면·로그인     | `/`, `/login`                                | 첫 화면 → [평가 시작] → 로그인. [평가위원] 이름→휴대폰→인증번호 단계형, [관리자] 아이디·비밀번호. SEC-01은 서버 검증 필요 |
| 메인                | `/admin`                                       | 처리할 일, 진행 사업                                                                                                           |
| 사업                | `/admin/projects`, `/admin/projects/:id`     | 사업 목록·등록. 사업 안에서는 왼쪽 메뉴에 공동 흐름 7단계                                                                     |
| 1 제안요청서 등록   | `…/:id/rfp`                                   | 업로드·작업 상태·실패 표시(DOC-01)                                                                                           |
| 2 평가기준 확정     | `…/:id/criteria`                              | 근거 쪽·쪽 미확인(DOC-02), AI 초안 검토·사람 확정(DOC-03)                                                                    |
| 3 제안서 등록       | `…/:id/proposals`                             | 제안사 등록(A·B·C 코드, 업체명은 관리자만), 업체별 제안서(DOC-01·06)                                                        |
| 4 평가위원 선정     | `…/:id/committee`, `/admin/evaluators`      | 후보 추가·CSV, 제척 사유·인원 부족·1회 추첨·위원장 지정(COM-01·03)                                                        |
| 5 평가 진행         | `…/:id/progress`                              | 평가일·발표 순서·시간·참석, 제출 현황, 발표 타이머(PROG-01)                                                                 |
| 6 결과·위원장 확인 | `…/:id/results`, `/eval/projects/:id/chair` | 전원 제출 전 잠금(RES-01), 위원장 확인 기록(전자서명 아님, RES-03)                                                             |
| 7 보고·완료        | `…/:id/close`                                 | 보고서 인쇄, 사업 완료(위원장 확인 후, CLOSE-01)                                                                               |
| 평가                | `/eval/projects/:id/…`                        | 서약 바텀시트, 자료 보기·질의응답(AI-01·02), 평가하기(EVAL-01·02·04), 제출 점검·잠금(EVAL-03)                             |

평가표 저장은 명시 저장 + 브라우저 임시보관 방식입니다. 저장 실패 시 입력을 유지하고, 새로고침하면 복원 여부를 묻습니다. 버전 충돌이 나면 서버 값과 비교하고, 저장하지 않고 이동하면 경고합니다. 임시보관은 서버 저장 성공·제출·로그아웃 시 삭제되고, 24시간이 지나면 앱 시작 때 지워집니다.

## mock 모드

- `src/api/mock.ts`가 API를 흉내 냅니다. 데이터는 localStorage에 남아 새로고침해도 유지되고, 요청마다 다시 읽으므로 두 탭 충돌도 재현됩니다.
- 합성 시드(`mockSeed.ts`): 평가 진행 중 사업 p1(제안사 3곳, 본위원 5·예비 2·위원장, 2명 제출), 준비 단계 사업 p2(제안사 미등록), 후보 10명.
- **화면 상단 "MOCK · 실제 서버 아님" 띠**의 [시연 도구]에서 느린 응답, 서버 오류, 저장 실패, 빈 데이터, 데이터 초기화, 전원 제출 시드 전환을 할 수 있습니다.
- 데모 로그인: [평가위원] 탭의 **가상 위원**(김가상 위원장, 정모의 본위원, 한가정 예비위원 등)을 누르면 인증까지 자동으로 진행됩니다. [관리자] 탭은 `admin / admin` 계정이 미리 채워져 있어 [로그인]만 누르면 됩니다. 기존 `gansa / demo` 계정도 사용할 수 있습니다.
- mock·시드·시연 도구·OTP 표시·데모 계정은 `VITE_USE_MOCK=1` 빌드에만 들어갑니다. 실제 빌드 산출물에서 해당 문자열이 없는 것을 확인했습니다.
- "mock 가정"이라고 표시한 규칙(산식, 위원장 결과 조회·확인 권한, 기준 재확정 금지, 제척 기준)은 담당자와 합의하지 않은 임시 규칙입니다.
- **mock 성공은 실제 서버 통합 성공이 아니며, 인수 기준 통과도 아닙니다.**

실제 모드에서 인증 API가 없으면 "인증 API 미연결" 안내만 보여 줍니다. 개발용 신원으로 우회하지 않습니다.
