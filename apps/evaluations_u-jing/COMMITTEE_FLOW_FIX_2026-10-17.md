## 실제 이용 순서

1. 부서관리자로 로그인 → 사업 등록에서 평가일 입력. 날짜를 아직 정하지 않았으면 비워 두고 사업 정보 수정에서 입력할 수 있다. 현재 설계는 날짜 단위이며 시작·종료 시각 필드는 없다.
2. 사업 선택 → 왼쪽 **위원 풀**에서 개별 또는 엑셀 등록.
3. 사업의 **평가위원** 단계에서 규칙 설정.
   - 풀 선정: 정원 7~9명, 분야별 합계 일치 → 저장 → 3배수 선정. 부족하면 전체 추첨 중단.
   - 직접 선정: DIRECT 규칙 저장 → 위원 풀에서 **이 사업 직접 등록**, 또는 연락·초청의 **사업 후보 추가**. 추첨하지 않는다.
4. 연락·초청에서 오프라인 전화 결과 저장 → 수락한 본위원과 예비위원 선택 → 명단 확정.
5. **참석·위원장**에서 평가회차 준비. 확정 명단과 문서 담당 모듈의 승인 평가표 수신이 필요하다.
6. 각 위원이 일반 입장 화면에서 이름·휴대전화 뒤 4자리로 로그인 → 동의·본인 참석 확인. 로그인만으로 참석 처리하지 않는다.
7. 담당자는 참석자 새로고침 → 실제 평가인원 확정 → 그 명단 중 위원장 지정 → 평가 시작.
8. 실제 참여 위원에게 평가표 작성 권한 제공 → 저장 → 점수 확인 → 개인 서명 → 제출.
9. 전원 제출 → 지정된 위원장에게 결과 탭 개방 → 최고·최저 각 1명 제외 평균 확인 → 서명 → 최종 제출.
10. 담당자 결과 화면에서 최종 결과 확인·보고서 다운로드.

입장과 참석 확인은 초청 명단 기준이다. 평가표 작성은 실제 참여 명단과 OPEN 상태 기준이며, 위원장 최종 제출은 같은 회차의 위원장만 할 수 있다. 예비위원이 로그인했다는 이유로 자동 평가 권한을 주지 않는다. 평가회차 준비 이후 사업 식별 정보·평가일 변경은 서버에서 막으며, 화면의 잠금도 일치시켰다.

이번 수정에 신규 DB 테이블은 필요하지 않았다. 날짜 테이블과 명단·참석·권한 테이블을 재사용했다. admin/evaluation SQLite 분리, 로컬 FK와 outbox/inbox 참조 동기화 방식은 유지한다. 인증된 일반 로그인 검색도 부서 풀 전체를 공개하지 않으며, 같은 사업에서 같은 이름·뒤4자리가 중복되면 임의로 한 명을 선택하지 않는다.

원본 `v2` 파일 수정 없이 `src/bindings/common.js` 및 해당 화면의 `binding.js`로 연결했다. 사용자 요청에 필요한 추가 입력은 사업 등록의 평가일과 복수 초청 시 사업 선택이다. 기존 화면 레이아웃·CSS·아이콘을 재설계하지 않았다.
